# ADR-0002: フロントエンド構成・画面方式・状態の所在

- ステータス: 採用
- 日付: 2026-06-24
- 決定者: 作者（dekka）／参謀システム（devil 指摘起点）

## コンテキスト

ADR-0001 で「Tauri v2 + Svelte」を採用した。実装着手（#1 雛形）にあたり、後続の
#2（コアロジック）・#3（メイン UI）・#4（ウィンドウ挙動）・#5（設定）すべての足回りを
規定する 3 つの論点を、手戻りを避けるため雛形段階で確定しておく。

1. Svelte の使い方（SvelteKit か、プレーン Svelte か）
2. 2 画面（メイン／設定）の実現方式
3. タイマー状態の「真実の所在」（Rust か フロントか）

## 決定

### 1. プレーン Svelte + Vite + TypeScript（SvelteKit を採用しない）

`create-tauri-app` の svelte-ts テンプレートは SvelteKit ベースだが、本アプリは小さな常駐
ウィジェットであり、ルーティング/SSR/プリレンダは不要。SPA で十分（Tauri 公式も SPA を推奨）。
重量級要件に反する依存を避けるため、プレーン Svelte + Vite に置き換える。

### 2. メインと設定は「別ウィンドウ」

- **メインウィンドウ**: 画面隅に小さく常駐・最前面（spec の中核体験）。情報は残り時間とフェーズのみ。
- **設定ウィンドウ**: 項目が多く相応の面積が要る。メインの「邪魔にならない小ささ」と設定の情報量は
  同一ウィンドウ内で両立しにくいため、設定は別の `WebviewWindow` として開く。

実装上の含意:
- 設定ウィンドウは #5 で追加する。その時点で `capabilities` を `["main"]` から
  `["main", "settings"]` 相当に拡張する（現 `default.json` のコメントに将来拡張の旨を残す対象）。
- 画面間のデータ受け渡しは「永続化された設定（単一の真実）＋変更イベント」で行い、ウィンドウ間で
  状態を直接共有しない。設定ウィンドウは設定を書き、メインはイベントで再読み込みする。

### 3. タイマー状態は Rust が権威（authoritative）を持つ

ADR-0001「コアロジックは Rust」・DoD「コアロジックのみ Rust 単体テスト」に従い、タイマーの
状態機械（フェーズ／残り時間／サイクル番号／サイクル数の 0=手動・有限 N・無限の扱い）は Rust 側に置く。

- **純粋な状態遷移ロジック**として実装し、`#[cfg(test)]` で単体テストする
  （「現在状態 + 経過時間 → 次状態」を時計に依存せず検証できる形）。
- 実時間の駆動（tick の呼び出し）は **Rust 側のランタイムタスク**が持つ。フロント（WebView）は
  tick を駆動しない（バックグラウンドタブで止まる JS タイマーを避けるため）。フロントは薄い表示層に
  徹し、操作（start/pause/reset/skip）を `invoke` で Rust に送り、状態更新をイベントで受け取る。
- Rust ランタイムは「前回 tick からの実経過秒」を**単調時計（`Instant` 差分）**で算出して `tick` に
  渡す。固定の `tick(1)` をインターバルで呼ぶ素朴実装はドリフトし、スリープ復帰でずれるため避ける。
- 時間モデルは **tick(経過秒) を採用し、deadline（終了時刻）モデルは採らない**。ポモドーロは精度が
  非クリティカルで、単調時計駆動ならドリフト/スリープ問題は実用上回避でき、状態機械を純粋に保てるため。
  （deadline モデルは #3 の境界跨ぎ処理を多少簡素化しうるが、動作済みのコア実装を作り直す利が薄い。）

## 検討した代替案

- **2 画面 = 単一ウィンドウ内でのコンポーネント切替**: 最も単純だが、小型ウィジェット内に設定 UI を
  詰めると「邪魔にならない」要件と衝突する。開くたびにウィンドウを拡大/縮小する案も挙動が煩雑。→ 不採用。
- **状態をフロント主導（UI が setInterval で tick、Rust は遷移計算のみ/または全部フロント）**:
  Rust 単体テスト方針・「コアロジックは Rust」と整合しないため不採用。

## 結果と影響

- ポジティブ: #2 以降の責務分担が明確（Rust=状態の真実とロジック、Svelte=表示と操作）。
  メインの軽さと設定の情報量を両立できる。コアロジックを時計非依存で単体テストできる。
- トレードオフ: ウィンドウが 2 つになり、`capabilities` とウィンドウ生成のコードが少し増える。
  Rust↔フロントの IPC（command/event）設計が必要。
- 見直しトリガー: 設定項目がごく少数に収まり別ウィンドウが過剰になった場合は、単一ウィンドウ切替へ
  の差し戻しを再検討する。

## 関連メモ（本 ADR の対象外だが追跡する事項）

- **CSP**: 現状 `tauri.conf.json` の `csp` は `null`。オフライン完結・バンドル音源のみ読む構成なので
  最小 CSP に締められる余地がある。GUI 実機で破綻しないことを確認できる段階（#6 音源／#7 ビルド）で
  ハードニングする。
- **opener プラグイン除去**: #1 で除去したが、理由は「軽量化」ではなく「現時点で外部リンクを開く機能が
  ないため（YAGNI）」。将来クレジット/ライセンス表記から出典 URL を開く要件が確定したら再追加する。

### #2（コアロジック）レビューで挙がった、#3 / #6 への申し送り

- **毎秒 IPC を避ける（#3）**: 軽量要件（アイドル時 CPU 最小）のため、毎秒フルスナップショットを emit
  しない方向を優先検討する。Rust はフェーズ境界・状態変化時にイベントを送り、残り秒のカウントダウン表示は
  フロント側で「残り秒 + ローカル時計」から補間する（真実は Rust、表示の補間はフロント）。
- **catch-up 時の通知音（#6）**: `tick` は複数フェーズ境界を一度に返しうる（スリープ復帰など）。過去に
  遡って発生したイベントの音を連続再生しないこと。最後の遷移のみ鳴らす等、上位（#3/#6）で消費を制御する。
- **skip 由来 vs 時間切れ由来の鳴らし分け（#6）**: `skip()` と `tick()` は別メソッドなので、呼び出し側で
  発生原因を区別できる。手動 skip の遷移では通知音を鳴らさない、といった制御は `TimerEvent` に原因種別を
  持たせずとも実現できる（必要になるまでイベント型は増やさない）。
- **設定変更の即時反映（#5）**: `set_config` は Idle のときのみ reset し、実行中は進行中セッションを
  壊さず次フェーズ以降に反映する。別ウィンドウで設定保存しても走行中タイマーが巻き戻らない。
